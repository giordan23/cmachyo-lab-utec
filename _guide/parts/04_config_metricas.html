Dos archivos base que usan todos los demás: uno lee la configuración y falla temprano si falta algo; el otro declara las métricas antes de que exista el código que las incrementa.

📖 Teoría · "fallar al arrancar" vs "fallar en la primera solicitud"

Si falta OPENAI_API_KEY, hay dos momentos para enterarse: al arrancar la API (un mensaje claro en la consola del desarrollador) o cuando el primer asesor envía una solicitud (un error 500 en producción). Settings.validar() elige lo primero. Lo mismo para un proveedor mal escrito (LLM_PROVIDER=gpt) o un número con coma decimal (0,55), error típico con configuración regional en español.

🔎Qué hace cada parte

  • decode_env_bytes — mira los primeros bytes: FF FE/FE FF es UTF-16 (PowerShell 5.1); si no, UTF-8 y utf-8-sig descarta el BOM del Bloc de notas.
  • load_env — override=False: una variable ya definida en el sistema gana sobre .env. Las pruebas lo aprovechan para forzar el modo sin claves.
  • Settings — una clase en vez de constantes sueltas: cada Settings() relee el entorno, así una prueba puede cambiar una variable y crear otra configuración.
  • validar() — las tres reglas de arranque: proveedor conocido, clave presente para el proveedor real, combinación coherente.
📖 Teoría · métricas de Prometheus en 4 tipos… usamos 3
  • Counter (_total): solo sube. Se consulta con rate() o increase(). Ej.: solicitudes, tokens, errores.
  • Gauge: sube y baja. Ej.: tamaño de la cola del analista.
  • Histogram: cuenta observaciones en "cubetas" (buckets) y permite percentiles con histogram_quantile(). Ej.: latencia, confianza del router.

Cardinalidad: cada combinación de etiquetas es una serie nueva en Prometheus. Por eso las etiquetas son valores de listas cerradas (ruta, dictamen, proveedor). Nunca el DNI, el id de la solicitud o el texto libre: además de reventar Prometheus, sería una fuga de datos personales.

Series en cero: un contador con etiquetas no aparece en /metrics hasta su primer incremento, y Grafana mostraría "No data". inicializar_series() crea las combinaciones conocidas en 0 al arrancar.

🪟Un ayudante para Windows y Docker

Paso 4

rules/ · las reglas en un solo lugar y el PDF

20 min

Pediste las reglas en PDF: aquí las generas. Pero el detalle importante es de dónde salen: el mismo archivo alimenta el PDF (que lee el RAG) y las guardas (que ejecuta el código).

📖 Teoría · una sola fuente de verdad

Si el PDF dijera "cuota/ingreso máximo 30%" y la guarda en código usara 35%, el LLM explicaría una regla y el sistema aplicaría otra: el analista vería una justificación que contradice el dictamen. En un banco real el PDF lo publica Riesgos y alguien lo traduce a código; aquí lo resolvemos por construcción: rules/politicas.py define los parámetros una vez, y el texto de cada artículo se arma con f-strings que leen esos parámetros.

Las pruebas del paso 5 lo verifican de punta a punta: extraen el texto del PDF y lo comparan con la fuente artículo por artículo.

🔎Qué hace cada parte

  • PARAMETROS — los límites duros: edad, ratios, antigüedad, monto de comité. Son los que leerá app/guardas.py.
  • CAPITULOS — 6 capítulos y 16 artículos. Cada uno tiene un id ("4.2") que será la cita en todo el sistema.
  • ENCABEZADO_ARTICULO — "Artículo 4.2 - Relación cuota / ingreso". La ingesta corta el PDF buscando exactamente este patrón.
  • invariant=1 — sin fecha ni identificador aleatorio: el PDF es idéntico en cada ejecución (útil para pruebas y control de versiones).
  • Fuente Helvetica de reportlab: cubre tildes y ñ (Latin-1) pero no símbolos como "−" (menos tipográfico) o "→". Por eso el texto usa "-".
